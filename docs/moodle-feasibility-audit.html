01

Employee accounts & data model

Employee Code as the native username

Native — with a normalization caveat

PARAM_USERNAME cleaning happens in clean_param_value_username(). It force-lowercases the value and, unless $CFG->extendedusernamechars is set, strips everything except -.@_a-z0-9.

public/lib/classes/param.php:1281–1295
$param = core_text::strtolower($param); // MDL-16919 if (empty($CFG->extendedusernamechars)) { $param = preg_replace('/[^-\.@_a-z0-9]/', '', $param); }
public/lib/db/install.xml:878, 924
<FIELD NAME="username" TYPE="char" LENGTH="100" .../> <INDEX NAME="username" UNIQUE="true" FIELDS="mnethostid, username"/>

Uniqueness on username is DB-enforced. A code like VRB-EMP-001 survives; something with mixed case or a slash would be silently mangled. Compare that to idnumber — also native, 255 chars, unrestricted charset — but its index is non-unique (install.xml:920), so uniqueness there is only whatever the app layer enforces.

Recommend

Store the human-readable Employee Code in idnumber (preserves formatting, already a first-class login-adjacent field), and derive the DB-unique, charset-safe username from it at account-creation time.

Two viable mappings — pick on reportability, not just simplicity

OptionContent-entryGate mechanicsReportability
A. 1 course = 1 moduleSimplest mental model per module; but many courses to create per categoryRestrict Access between courses is awkward — Moodle's completion/availability chain is built to gate within a course, not between separate coursesCross-module rollups need a category-level query (core_course_category::get_courses()) across many course records
B. 1 course = 1 category, sections/activities = modulesSlightly more setup per category, but one enrolment event unlocks the whole categoryRestrict Access at section/activity level is exactly what Section 03 verifies works end-to-endOne course = one leaderboard scope; simpler joins

Recommend Option B: the completion-gated, section-based structure is what Moodle's own availability engine is designed around (see Section 03), and it keeps "leaderboard per category" a single-course query instead of a cross-course aggregation.

05

Reporting / shared query layer

Custom plugin required — architecture recommendation

One local plugin (e.g. local_vrblms) should own the SQL against {quiz_attempts}/{quiz_grades}/{cohort_members}/{user_info_data}, exposed as internal service classes — a leaderboard block and an admin report both call into the same classes instead of each carrying their own copy of the join.

Confirmed clean slate
public/local/ → only readme.txt, upgrade.txt (no existing plugin to conflict with)

public/blocks/ and public/report/ (e.g. report/log's settings.php / lib.php / version.php / db/ layout) are the structural templates a new block and report plugin would follow — both are thin presentation layers over the same local_vrblms API, which is also where certificate-qualification logic (Section 06) would live so it can reuse the identical ranking query.

06

Certificates

Not installed locally — do not assume

No certificate plugin exists anywhere in this tree — find public/mod public/local -iname "*cert*" returned nothing. Whatever plugin gets used (e.g. a Custom Certificate–style module), its presence, its version.php compatibility with 5.1.5, and its maintenance status all have to be verified after it's actually fetched and installed — none of that can be claimed from this install as it stands today.

A native fallback that already does the hard part

Native — arbitrary user_id, confirmed

Core badges can be issued programmatically for any user id, independent of whether Moodle's own criteria engine considers that user to have "earned" it — which is exactly the shape needed, since qualification here is decided by custom ranking logic, not course completion state.

public/badges/classes/badge.php:428
public function issue($userid, $nobake = false) { ... $issued->userid = $userid; $result = $DB->insert_record('badge_issued', $issued, true); \core\event\badge_awarded::create($eventdata)->trigger();

The gap: badges are OpenBadges (image + JSON assertion), not a typeset, printable PDF certificate with name/course/date layout. Whether that satisfies what the client actually expects as "a certificate" is a product question, not a technical one — flagged below as the one item worth resolving before committing to either path.

Resolve before build

Fetch the intended certificate plugin, read its version.php against 2025100605.05 / branch 501, and check its repo's last-commit date — then decide between it and a core_badges::issue()-based wrapper. Don't default to the plugin on memory of it being "the standard choice."

Core modification check

No BLOCKER found

Every requirement traced to a real, non-core extension point rather than a gap that would force touching core: cohort event_added observers, the enrol_plugin type, the availability_completion condition class, the gradebook API, and badge::issue() for arbitrary users. None of Sections 01–06 needed to reach into public/lib, public/mod/quiz, or public/completion source itself — every hook used is a documented extension surface already exercised by core-bundled plugins in this same tree.

Overall verdict

This installation is a safe technical foundation to commit to. Every requirement — username/profile modeling, brand-and-region cohort membership, cohort-synced enrolment, the completion-plus-availability quiz-gating chain, and the raw attempt/timing data needed for a leaderboard — traces to real, current, core-bundled code at this exact 5.1.5 branch, and none of it requires modifying core. The one open item is Section 06: no certificate plugin is installed, and that choice (a fetched third-party plugin vs. a core_badges-based wrapper) should be resolved with a short prototype — install the candidate plugin, confirm its version.php against branch 501, and mock up whether a badge-issued asset reads as "a certificate" to the client — before that piece of the architecture is locked in. Everything else in this report is ready to build against as-is.
